# Как работает TinyTalk Reason

## 1. Числовое распознавание

`features` кодирует слова и фрагменты символов в разреженный нормированный
вектор x длины 2048. `forward` вычисляет h=tanh(W1*x+b1), затем
p=softmax(W2*h+b2). Максимальная компонента p предлагает намерение.

Это обучение с градиентами, не «предсказание без математики». Для 11 классов
используется 98891 обучаемых float-параметров (395564 байт без меток и заголовка).
Структура Model резервирует место для 256 классов, поэтому занимает больше файла
модели. Размер State измеряется тестами отдельно от полного RSS процесса.

## 2. Память

State содержит цель, список чисел-калорий, длительности таймеров, пары
object/owner, номера исходных реплик, текущую тему и ожидаемый параметр.
Полный текст истории не хранится. Дальнее упоминание, которое не представлено
этими полями, восстановить нельзя. Последняя версия факта заменяет старую;
полная история правок доступна только в журнале диалога, если его сохранять снаружи.

При добавлении события k: E_new = E_old ∪ {e_k}.
При исправлении: E_new[k] = corrected_value, длина E не меняется.
При вопросе об остатке: remaining = goal - sum(E).
При передаче: owner(x)=a и transfer(x,a,b) => owner_new(x)=b.
Несовпадение отправителя с owner(x) приводит к CONFLICT без передачи.

Все эти гарантии условны: они применимы к корректно разобранной конструкции.
Движок не доказывает, что произвольная русская фраза разобрана верно.

## 3. Основные функции

| Функция | Что делает |
|---|---|
| normalize | Проверяет UTF-8, ограничивает длину, приводит русский/ASCII к нижнему регистру |
| numbers | Извлекает до двух целых чисел; отклоняет отрицательные, дроби, слишком большие |
| word / has | Проверяет слово или вхождение фрагмента; это эвристика, не морфологический анализ |
| relation | Разбирает контролируемые факты владения, вопросы и передачи |
| fact_index | Находит объект в массиве, O(число объектов) |
| respond | Предлагает намерение через MLP, применяет проверки и обновляет State |
| say | Записывает код результата и пользовательский ответ |
| proof | Записывает основания выполненного правила |
| features / forward | Признаки и вычисление MLP, унаследованы от TinyTalk |
| checkpoint | Чтение/запись обученных весов |
| main | CLI, интерактивный/пакетный режим, прогон TSV-тестов |

`tiny_base.c` включается в reason.c с переименованием его main, чтобы обе программы
использовали точно один и тот же код MLP. Это компактный прототип; при развитии
его стоит разделить на библиотеку с публичным заголовком и два CLI.

## 4. Почему это отличается от исходного TinyTalk

Исходный TinyTalk всегда выбирает одну готовую строку по одной текущей реплике.
Reason хранит значения, полученные во время диалога, и вычисляет новый ответ из них.
Число 2234 в ответе не нужно хранить как отдельный класс сети. Но набор операций,
которые над этими числами разрешены, задаётся кодом человека.

Контекст не получается сам по себе от многократного обучения `data.txt`.
В этой реализации его обеспечивает State и правила Update.

## 5. Что доказали тесты и чего они не доказывают

Регрессионные диалоги проверяют предусмотренное поведение. Генератор в C создаёт
200 диалогов с новыми числовыми комбинациями и сверяет ответы с арифметическим
эталоном; это проверка кода состояния, а не обобщения русского языка.
Тест MLP из пяти вопросов использует знакомые формулировки и является smoke-тестом.
Сравнение --rules-only показывает, что MLP участвует в ответах, но baseline можно
улучшить дополнительными правилами. Оно не доказывает превосходства нейросети.

ASan/UBSan проверяют выполненные сценарии, не весь набор возможных входов.
LeakSanitizer отключён в скрипте для совместимости с ограниченным Linux-стендом.
CPU seconds в тестовом выводе включают разбор и печать и не включают загрузку
модели: это диагностическое время, не достоверный benchmark задержки или энергии.

## 6. Следующий исследовательский эксперимент

Заморозить обучающие фразы; собрать независимые диалоги от людей, не участвовавших
в написании правил. Отдельно оценить правильность намерения, слотов, ссылок,
исправлений, итогового состояния и отказов. Сравнить: сильные правила без сети,
исходный классификатор без памяти, классификатор с историей, гибрид со State.

Нужны разбиение по диалогам и семействам формулировок, отдельная валидация порога
0.85, многократные измерения задержки после прогрева и измерение RSS. Публиковать
как успешные ответы, так и ошибки. Только затем делать вывод о выгоде и новизне.
